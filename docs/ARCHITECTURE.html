Section 03

Request lifecycle

Every request flows through src/hooks.server.ts → SvelteKit router → either a route's +page.server.ts load/form actions, or a +server.ts REST handler.

Browser │ ▼ hooks.server.ts (src/hooks.server.ts) │ 1. event.locals.user = await getSessionUser(cookies) │ 2. ~1% chance: fire-and-forget cleanupExpiredSessions() │ 3. If POST/PUT/PATCH/DELETE to a trip-edit route AND trip ended → 403 │ 4. await resolve(event) │ 5. Set Server-Timing header for the dev PerfBadge ▼ SvelteKit Router │ ├──► /routes/.../+page.server.ts (load + form actions) │ │ │ ▼ │ Server logic → Prisma → Supabase Postgres │ └──► /routes/api/.../+server.ts (REST handler) │ ▼ Server logic → Prisma / Stripe / Google / Resend

Key properties

  • Single auth checkpoint. event.locals.user is hydrated once in hooks.server.ts:34; downstream handlers read it without touching the DB again.
  • No middleware chain. SvelteKit doesn't have Express-style middleware. Cross-cutting concerns (auth, key checks, CORS) are explicit helper calls inside each handler.
  • Lazy maintenance. Session GC piggybacks on real traffic (1% probability per request) instead of a dedicated cron.
  • Closed-trip write gate. Lines 43–66 block writes to /trips/[tripId]/(guests|itinerary|rooms|settings) and /api/trips/[tripId]/update once checkOutDate is in the past.
Concern: the closed-trip gate covers four route prefixes and one API path explicitly. Any new write endpoint added outside this list (e.g. a new /api/trips/[tripId]/rooms/... write) won't be gated automatically. Worth replacing with a per-handler guard helper.

Reviewer note space. Anything about the lifecycle that doesn't match how it actually behaves? Add notes here or to the markdown twin.

Section 04

Auth & sessions

Pure native-password + DB session cookies. No third-party identity provider, no OAuth.

ConcernImplementation
Password hashingbcryptjs at signup/login (src/lib/server/user-auth.ts)
Session modelPrisma Session row — userId, opaque UUID token, expiresAt
Web cookieuser_session · httpOnly · sameSite=strict · secure in prod · 7-day TTL
Mobile tokenSame Session table, 90-day TTL, issued via /api/mobile/auth, sent as Bearer header
LogoutdestroySession() deletes the row + clears the cookie
GCcleanupExpiredSessions() fires ~1% of requests from hooks.server.ts

requireAuth() wraps getSessionUser() and returns null when no user — handlers throw redirect(302, '/login') themselves. This is per-handler, not a global gate.

Concern: the 7-day web cookie / 90-day mobile token split is arbitrary. If the same Session table is shared but TTL differs based on issue site, a long-lived mobile token compromised on a device persists much longer than a web session. Document the threat model or unify.
Section 05

Data model — orientation

Full schema is in prisma/schema.prisma. Trip is the center of the graph.

User ──┬── Session ├── RSVP ──── Trip ├── TripMember ├── Invoice ├── ChatMessage / DirectMessage ├── Notification ├── Friendship / FriendRequest └── HouseholdMember Trip ──┬── Room ── Bed ├── RoomAssignment ├── RSVP ├── Household ── HouseholdMember ├── Activity ── ActivityParticipant ├── MealPlan ── MealSlot ── MealSlotAttendance ├── Poll ── PollOption / PollVote / PollWatcher ├── CaptionThisRound ── Caption / Vote ├── TripGame ├── Invite ├── Invoice ├── ExtraCostRule ── GuestExtraSelection ├── ChatMessage ├── TripFile └── TripActivity (append-only log)

Pricing-critical fields on Trip

  • pricingModel — PER_PERSON | PER_PERSON_PER_NIGHT | PER_ROOM | PER_BED
  • totalCost, costSharingEnabled
  • bedWeights (JSON), sharingExponentAlpha, privacyPremiumP — backend tuning knobs (PRD §5.1)
  • publishFeePaymentIntentId — uniqueness gate for the $25 fee

Cost-re-approval fields on RSVP

  • acceptedEstimateLowCents, acceptedEstimateHighCents — the range the guest accepted at RSVP time
  • originalRangeMinCents, originalRangeMaxCents — frozen originals
  • approvedCostShareCents — most recent re-approved share (raises the ceiling)
  • costApprovalStatus (approved | pending | hostApproved), costReapprovalReason, reApprovalDeadline
Confusion: two parallel sources of truth for the accepted range — (originalRangeMinCents, originalRangeMaxCents) and (acceptedEstimateLowCents, acceptedEstimateHighCents). cost-reapproval.ts:64–65 falls back from one to the other (origMax ?? acceptedEstimateHighCents) — implying historical migration. Worth deciding which is canonical and dropping the other.

Legacy / superseded (audit before deleting): Reservation, GuestSubmission.

Section 06

Pricing engine

Three forms of the same enum coexist — keep them straight:

LayerFormExample
DB / REST APIlowercase_underscoreper_bed
Canonical (server math)UPPER_SNAKEPER_BED
UI / wizardkebab-caseper-bed
Confusion: three forms of the same enum across the codebase. Translation lives in a comment at the top of pricing.ts; calculatePrice() normalizes via .toLowerCase() and accepts both DB and canonical. Worth collapsing to one canonical form across all layers — pure technical debt.

6.1 Flow

+page.server.ts / +server.ts
        │
        ▼
calculatePrice(params)        (pricing.ts)
        │ switch on pricingModel
        │
        ├── per_room      → calculatePerRoomPrice()
        ├── per_person    → flat totalCost / headcount
        ├── per_person_per_night → totalCost / headcount / nights
        └── per_bed       → delegates to calculateReservationPrice()

6.2 Per-bed math (canonical model)

pricing-canonical.ts (1,200+ lines) implements the bed-weighting + privacy-premium model. The file references a PRICING.md cross-reference for the formula. High-level shape:

  • Each Bed has a weight by type (DEFAULT_BED_WEIGHTS: king > queen > full > twin > sofa > bunk).
  • Each Room has a privacy factor (default 1.0; private rooms up to 1.25).
  • Trip total $ is allocated across all sleep slots based on bedWeight × roomPrivacy, then multiplied by occupancy fraction per slot.
  • effectiveSleepSlots() computes how many slots a bed counts for given current occupancy.
  • quoteForUserId + provisionalPick let the quote flow simulate "what would this cost if I picked this bed?" without persisting.

None of these knobs are host-facing. Hosts pick a model; the rest is server-side tuning the team can adjust by editing constants.

Concern: the comment block in pricing-canonical.ts calls sharingExponentAlpha and privacyPremiumP "legacy" — but they're still part of the PricingSettings interface and stored on Trip. If they're legacy, deprecate and drop; if they're live, remove the "legacy" comment.

Reviewer note space — pricing engine. If PRICING.md exists somewhere with the actual formula, link it here. If not, worth writing.

Section 07

Cost re-approval

Implemented in src/lib/server/cost-reapproval.ts. The rule (PRD §5.2): an RSVP gets costApprovalStatus = 'pending' whenever its invoice total exceeds its personal ceiling. Decreases never trigger.

7.1 When the evaluator runs

CallerWhen
invoice-calculator.ts:201, :217After any invoice recompute (host changes, activity added, room/bed shuffled)
/api/trips/[tripId]/cost-reapproval/withdraw/+server.ts:85After a guest withdraws an RSVP (fewer splitters → others' shares go up)

It is idempotent — RSVPs already pending are skipped (cost-reapproval.ts:58).

7.2 The asymmetric check

const ceiling = r.approvedCostShareCents ?? origMax;
if (currentCents <= ceiling) continue;   // decreases or in-range: no-op
// else: mark pending, notify, set deadline
  • Ceiling = most recently re-approved share, or the original accepted high.
  • On approval, approvedCostShareCents is updated to the new value → ceiling rises → range only expands.
  • Deadline = 48 hours before Trip.checkInDate (cost-reapproval.ts:4–8).
  • Notification fan-out: writes a Notification row + sends a Resend email via sendCostShareReapprovalToGuest.

7.3 Decreases

Intentionally a no-op (PRD §5.2). The guest sees the lower share next time they log in. Keeps re-approval traffic focused on the only thing that matters: someone potentially owing more than they agreed to.

Reviewer note space — re-approval. Does the 48-hour-before-checkin deadline match how you want it to behave? What happens to a guest who doesn't re-approve before the deadline — auto-withdraw, host decides, or status sticks?

Section 08

Notifications

Event-driven by default (PRD §5.10). Almost every notification — invite received, RSVP accepted, room assigned, cost re-approval needed, waitlist promotion — fires in real time at the moment the event happens, via src/lib/server/notification-service.ts.

Each event writes a Notification row (in-app) and conditionally calls Resend (email) based on the user's notification preferences.

8.1 Scheduled jobs

Current vercel.json (will be slimmed for MVP):

{
  "crons": [
    { "path": "/api/cron/waitlist", "schedule": "0 12 * * *"  },
    { "path": "/api/cron/emails",   "schedule": "15 12 * * *" },
    { "path": "/api/cron/polls",    "schedule": "30 12 * * *" }
  ]
}

Planned for MVP — only poll lifecycle nudges, three times daily at 7am / 12pm / 8pm ET:

{
  "crons": [
    { "path": "/api/cron/polls", "schedule": "0 11 * * *" },   // 7am ET (UTC-4)
    { "path": "/api/cron/polls", "schedule": "0 16 * * *" },   // 12pm ET
    { "path": "/api/cron/polls", "schedule": "0 0 * * *"  }    // 8pm ET
  ]
}
Concern (DST drift): Vercel crons run in UTC. The 7am/12pm/8pm ET targets drift one hour at DST boundaries. Acceptable for MVP; for year-round precision, move the schedule decision into the handler.

/api/cron/waitlist and /api/cron/emails are slated for removal. Audit the upstream callers in cron-email-service.ts first — any event that currently relies on the batched send needs to be wired to the event-driven path before the cron is deleted.

8.2 Cron auth

src/lib/server/cron-auth.ts — if CRON_SECRET is set, the handler requires Authorization: Bearer <CRON_SECRET>. Vercel injects this header automatically when calling its own cron endpoints. Returns 401 when invalid; silently allows when unset (so local invocation works).

Concern: "silently allows when unset" is fine for dev but means a production deploy with missing CRON_SECRET leaves cron endpoints world-callable. Consider failing hard in production builds.
Section 09

External integrations

9.1 Stripe

Single flow: the $25 publish fee. File: src/lib/server/stripe.ts.

  • Key pairing guard refuses to start if STRIPE_SECRET_KEY and STRIPE_PUBLISHABLE_KEY are on different test/live modes (lines 25–50). Catches a common deployment footgun.
  • PaymentIntent: card-only (payment_method_types: ['card']) — hides Klarna / Amazon Pay / redirect-based methods.
  • Metadata: userId, purpose: 'platform_publish_fee', optional tripId.
  • Replay protection (verifyPublishPaymentIntent, lines 104–145):
    • status must be succeeded
    • amount must equal PLATFORM_PUBLISH_FEE_CENTS (2500)
    • currency must be usd
    • purpose and userId in metadata must match
    • publishFeePaymentIntentId must not already exist on any Trip — one PaymentIntent = one publish
  • No webhooks. Verification is request/response — the trip page polls /api/stripe/verify after the Payment Element confirms.
Concern (no webhooks): request/response verification means a successful Stripe payment with a flaky network on the return trip can leave a guest charged but the trip not marked published. The metadata replay-protection makes retry safe — the same PaymentIntent can verify on a refresh — but the user-facing failure mode needs a clear retry path. Worth testing.

9.2 Google APIs

  • Client: @googlemaps/js-api-loader + VITE_GOOGLE_MAPS_API_KEY → Places Autocomplete for the wizard's location field.
  • Server: GOOGLE_PLACES_API_KEY → Nearby Search / Text Search / Geocoding via /api/trips/[tripId]/activities/discover.

Keys are distinct because the client one is publicly visible (should be domain-restricted in Google Cloud); the server one should be IP-restricted to Vercel egress.

9.3 Resend

Transactional email. Templates live in src/lib/server/email/render/. Brand tokens come from src/lib/server/email/brand.ts, which mirrors theme.css (emails can't use CSS variables, so hex codes are duplicated).

Env: RESEND_API_KEY, RESEND_FROM_EMAIL (verified domain), RESEND_FROM_NAME, optional EMAIL_LOGO_URL.

9.4 Supabase

Used only for the Postgres database. The codebase imports @supabase/supabase-js but auth is fully native (bcryptjs + DB sessions). The Supabase service-role key is set but not exercised for auth.

  • App connection: Supabase pooler on port 6543
  • Migrations: direct connection on port 5432
Concern: if Supabase auth isn't used, why is the SDK imported? Either remove the dependency or document where it's needed. Carrying a 60kb SDK for no reason is debt.
Section 10

API surface

10.1 Web

REST endpoints at /api/* are SvelteKit +server.ts files. Conventions:

  • Input validation via Zod schemas in src/lib/server/validation.ts. createErrorResponse(code, message) standardizes error shape.
  • Authn check is per-handler (no global middleware). Write endpoints typically call requireAuth() then requireTripAccess().
  • Internal-only writes gate with requireInternalApiKey(event) and require X-Internal-Api-Key.
  • Rate limit via rate-limit.ts (in-memory token bucket; single-region appropriate).

10.2 Mobile

/api/mobile/auth handles login/register for a future native client.

  • Token-based: returns a session token in the JSON body; client supplies as Authorization: Bearer … on subsequent calls.
  • 90-day TTL for mobile sessions (web is 7 days).
  • CORS: src/lib/server/mobile-cors.ts returns permissive headers for native clients. The web app does not use these endpoints.

Native app isn't in v1 scope (PRD §6), but the surface is preserved.

Concern: a scaffolded API with no consumer drifts. Either ship the native app or freeze the mobile contract and version it — otherwise future schema changes will silently break a not-yet-built client.

Section 12

Deployment

  • Adapter: @sveltejs/adapter-vercel → Vercel serverless functions (Node 20 runtime).
  • Region: iad1 (US-East). Single region, matching the US-only launch.

Section 13

Performance

  • Server-Timing header added in hooks.server.ts:73. A dev-only <PerfBadge> reads it client-side via the Server-Timing / Resource Timing APIs.
  • Lazy session GC (1% per-request probability) avoids a separate scheduled job.
  • Prisma client singleton avoids cold-start connection storms.
  • Postgres connection pooler (Supabase 6543) handles per-function-invocation connections.
  • web-vitals package is installed — wire-up TBD; no visible reporting endpoint.
Concern: web-vitals is a dependency with no apparent consumer. Either wire it to a reporting endpoint (Vercel Analytics, custom) or remove.
Section 14

Known technical debt

  1. Legacy models. Reservation and GuestSubmission look superseded by RSVP + RoomAssignment. Audit before deleting.
  2. No error tracking. Sentry (or equivalent) needs to land before public launch.
  3. No analytics / event instrumentation. Re-approval funnel data is the single most important thing to measure.
  4. E2E test status unknown. Playwright tests exist in /e2e/ — confirm pass/fail status, wire into CI.
  5. Cron cleanup pending. waitlist and emails crons to be removed; upstream callers need event-driven rewiring first.
  6. DST drift on cron schedule. Vercel crons run UTC; ET targets drift one hour at DST boundaries.
  7. In-memory rate limiter won't survive multi-region deployment. Fine for iad1-only MVP.
  8. Mobile API scaffold is in place but unused. Ship the app or freeze and document.
  9. @sveltejs/adapter-auto in devDependencies alongside adapter-vercel. Config uses adapter-vercel; remove the auto package.
  10. Pricing enum tri-form (DB / canonical / UI) — collapse to one form.
  11. Two RSVP range sources (originalRange* vs acceptedEstimate*) — pick canonical.
  12. @supabase/supabase-js imported but not used for auth — drop the SDK if not needed.
  13. web-vitals installed but no consumer — wire or drop.
  14. "Legacy" knobs still live. sharingExponentAlpha, privacyPremiumP are tagged legacy in code but persisted on Trip and read by the pricing engine.

Reviewer note space — debt. Add or strike items. Anything here you want to actively schedule for v1, vs accept as v1.1 cleanup?
